# Контракт резервного копирования модулей — ПОСТОЯННЫЕ ПРАВИЛА

**Введён в Alpha 2.829. Обязателен для всех нынешних и будущих модулей.**

Резервная копия `.3diwell-backup` включает настройки и **все пользовательские данные**
установленных модулей (секция `module_data` payload schema v2). Проекты, задачи, файлы проектов,
managed-хранилище и история печати в копию **не входят** и restore их **не меняет** (guard
неизменности — fingerprint до/после с полным откатом при расхождении).

## Классификация (fail-closed)

Каждый установленный модуль обязан быть зарегистрирован (`app/config_backup/module_providers.py`)
как ровно одно из:

| класс | смысл |
|---|---|
| `persistent_data_with_backup_provider` | есть пользовательские данные И есть provider |
| `no_persistent_user_data` | доказано (forensic), что пользовательских данных нет |
| `backup_temporarily_unsupported` | данные есть, provider ещё нет — **полный export блокируется** |

- Модуль с данными без provider **не может молча пропускаться**: экспорт завершается ошибкой
  `manual_resolution_required` с точным именем модуля («Полная резервная копия невозможна:
  модуль не поддерживает сохранение данных»). Файл, называемый полной копией, при потере части
  данных не создаётся.
- Новый persistent-модуль без классификации = красный тест (`test_module_backup_contract.py`).
- **AGENTS-правило:** *A module with persistent user data must provide a permanent versioned
  backup provider before release.*

## Provider (ModuleBackupProvider)

Контракт: `module_id` (stable identity, НЕ display name; версия модуля — метаданные, не схема),
`backup_schema_version` (независимая), `data_class`, `export_snapshot(store)`,
`validate_snapshot`, `migrate_snapshot` (append-only цепочка модуля; схема новее ридера →
безопасный отказ), `build_restore_plan` (только чтение), `apply_restore` (только под журналом
multistore), `verify_restore`, `describe_scope`. Provider обязан: выдавать логическую
каноническую JSON-модель (НЕ raw SQL dump, НЕ ORM rows, НЕ pickle), быть детерминированным, не
обращаться к принтерам/сети/локали, не включать runtime-кэш, ничего не менять при inspect/plan,
иметь frozen-фикстуру и completeness-тест.

Провайдеры текущих модулей живут **в ядре** (module ZIP не меняются). Будущий модуль может
регистрировать собственный provider тем же контрактом.

**Какие модули входят в копию (R-125, data-safety-01).** Все установленные: загруженные,
**отключённые пользователем** и найденные на диске, но **не загрузившиеся** (у последних должен
быть читаемый манифест с допустимым id). Хранилище модуля от состояния загрузки не зависит; у
отключённого в копии `enabled=false`. Базы, которой ещё нет (модуль ни разу не запускался),
экспорт и план читают как пустую и не создают. Удалённый модуль (папки нет) в копию не входит, а
его данные при восстановлении по-прежнему требуют установленного модуля.

**Необязательные части контракта (R-125).** `TableSpec.unique` — наборы колонок с ограничением
UNIQUE в схеме модуля (кроме ключа); `restore_conflicts(store, snapshot)` находит строки копии,
чьё уникальное значение на цели занято другой записью. Хранилище с `has_table(name)`
(`SqliteModuleStore`) позволяет найти таблицы копии, которых у модуля на цели нет.

## Forensic-состав текущих модулей (Alpha 2.829, обновлено R-125)

- **inventory** (`farm_inventory.db`), **backup v2**: включены `inv_vendors/inv_filaments/
  inv_locations/inv_items/inv_spools/inv_ledger` + настройки `inv_settings`, а с v2 — мобильная
  приёмка: `inv_mobile_codes` (коды QR/штрихкодов, в том числе `nfc:bambu:<uid>`),
  `inv_mobile_nfc` (метки NFC катушек), `inv_mobile_label_batches` и `inv_mobile_labels`
  (подготовленные наклейки; номер наклейки уникален в партии). Код на наклейке несёт
  `inv_settings.mobile_server_id` — он восстанавливается настройками. Исключены
  `inv_pending_prints` (runtime-трекинг печатей) и `inv_mobile_ops` (квитанции повторов запросов
  телефона). Миграция v1→v2 добавляет мобильные таблицы пустыми: старая копия их не трогает.
  Привязки катушек — по stable printer ID; отсутствующий принтер НЕ удаляет катушку (warning в
  плане, привязка сохраняется данными).
- **cost** (`farm_cost.db`). **backup v1** описывала прежнюю «Себестоимость печати»:
  `cost_config` (настройки), `cost_printer_settings`, `cost_calculations`; `cost_run_durations`
  (история печати) исключён. С 3.0 под тем же id стоит «Расчёт заказа» (слово владельца
  12.09.2026), и **backup v2** описывает его настоящую схему (`modules/cost/backend.py`, DDL):
  `order_config` (настройки строкой `global`; обычная таблица — у неё `updated_at NOT NULL`),
  `order_model_rates`, `order_printer_rates`, `order_printer_models`, `order_sequence`, `orders`.
  **`order_files` не входит**: строки описывают копии файлов моделей в `cost_order_files\` по
  абсолютному пути, а файлы копия не несёт (вложения — формат контейнера v3, решение владельца);
  заказ восстанавливается без файлов, и это написано в окне копии. Особые правила: номер заказа
  (`orders.order_number`, UNIQUE), занятый на цели ДРУГИМ заказом, блокирует восстановление
  модуля на этапе плана; счётчик `order_sequence` применяется как MAX(текущее, из копии) и
  проверяется «не меньше», чтобы номера не пошли повторно. Миграция v1→v2 переносит данные
  прежней «Себестоимости» как есть в `extensions["x-legacy_cost_v1"]` и НЕ применяет их (модуль
  3.0 этих таблиц не создаёт): старая копия 2.x больше не откатывает всё восстановление, а план
  пишет «данные прежней «Себестоимости печати» из этой копии не восстанавливаются».
- **quality** (`farm_quality.db`): **no_persistent_user_data** — доказано: 0 write-маршрутов
  (все 4 GET), все колонки `print_runs/print_run_materials/print_run_event_aliases`
  захватываются автоматически из событий печати = журнал ИСТОРИИ ПЕЧАТИ, которую restore
  менять запрещено. Attachments нет ⇒ контейнер v3 не требуется (решение A ЭТАПА 5).
- **messengers** (`farm_messengers.db`): настройки `msg_settings` без ключей ботов
  (`msg_secrets` не входит); на другом компьютере каналы подключаются заново.
- **appearance** («Оформление и темы», 3.0): **no_persistent_user_data** — модуль только
  интерфейса: бэкенда, базы и маршрутов нет, темы лежат в браузере (`localStorage`, ключи
  `fm_appearance_*`). Без классификации его установка блокировала бы полный экспорт
  (fail-closed) — это поймала проверка на настоящем сервере 12.09.2026.
- **camera_wall** («Видеостена», R-125): **no_persistent_user_data** — `backend.py` нет, значит
  нет ни базы, ни маршрутов; источники камер, выбор и раскладка лежат в браузере
  (`localStorage`, ключи `3diwell.camera_wall.*`). До классификации установленная «Видеостена»
  блокировала полный экспорт (409 `manual_resolution_required`). Полнота реестра проверяется по
  настоящим модулям: `modules/*/module.json` и `app/module_catalog.KNOWN_MODULE_RELEASES`
  (`tools/test_module_backup_contract.py`).

## Ссылочная целостность (Alpha 2.830)

- **Структурная целостность — фатальна**: строка-объект, непустой ключ, уникальность ключа,
  типы, длина строк. Нарушение = реальное повреждение снапшота → `validation_failed`.
- **Внутренние ссылки (`refs`) — СОВЕТУЮЩИЕ, НЕ фатальные**: непустая ссылка на ОТСУТСТВУЮЩУЮ
  запись (пользователь удалил локацию/филамент, а товар/катушка ещё на неё ссылаются) — это
  ЛЕГИТИМНОЕ состояние живой БД, а не повреждение. Такая запись **сохраняется как есть**
  (значение НЕ обнуляется, НЕ заменяется дефолтом), связь считается неактивной; план даёт
  `dangling_internal_ref` (счётчик, без значений). Тот же принцип, что и для внешних ссылок на
  принтеры (`missing_printer_ref`). Это root cause дефекта Alpha 2.829 (`validation_failed:
  broken ref inv_items.location_id -> inv_locations` на реальной пользовательской копии): строгая
  проверка отвергала валидные данные и делала копию невосстановимой.

## Само-проверка экспорта — ПОСТОЯННЫЙ инвариант (Alpha 2.830)

**`export_success => same-version inspect/validate/plan_success`.** Экспорт ОБЯЗАН до выдачи
файла выполнить полный обратный проход по фактическим байтам копии тем же кодом, что и restore
(`app/config_backup/self_check.py`): decode → migrate → validate → `build_full_plan` против
текущего состояния → план не требует manual_resolution для собственного состояния. Если проверка
не прошла — **файл не создаётся**, пользователь видит понятное сообщение, `audit` пишет
`validation_failed` (НИКОГДА `result=ok` на невалидной копии). Farm Manager не имеет права выдать
копию, которую сам же не прочитает.

## Безопасные ошибки проверки (Alpha 2.830)

`BackupError` НИКОГДА не уходит как unhandled 500. Наружу — только структурированный безопасный
ответ: `reason` (код) + `stage` (parse/migrate/plan/apply/self_validation) + `section`
(core|printers|modules) + `module_id` + `field_path` (schema-путь «таблица.колонка»). НИКОГДА
значения, секреты, пути ФС, traceback, raw SQL, фрагменты payload. UI показывает понятный текст
с названием модуля (например «…не прошла проверку данных модуля „Складской учёт“. Файл не был
применён»), кнопка «Повторить проверку» повторяет ТОЛЬКО inspect/plan, не apply.

## Семантика restore

- **UPSERT по стабильным ключам**; записи «только на текущей машине» НЕ удаляются.
- **Старые копии (payload v1, 2.827–2.828) НЕ содержат module_data**: секция мигрируется как
  **ОТСУТСТВУЮЩАЯ (None)**, а не пустая — данные модулей на цели **не очищаются и не
  заменяются**; план явно пишет: «Данные модулей отсутствуют в этой версии резервной копии и
  не будут изменены». Миграция «replace with empty» запрещена навсегда.
- **Missing module**: если в копии есть данные модуля, а модуль не установлен — план показывает
  «Для восстановления данных требуется модуль <id>», полный restore блокируется
  (`manual_resolution_required`); пользователь ставит модуль либо явно исключает секцию.
- **Данные модуля не ложатся на эту установку (R-125)** — тот же отказ, но ДО любых изменений,
  а не откатом всего посреди применения: `module_not_initialized` (файла базы модуля на цели
  нет — модуль ни разу не запускался: включить и перезапустить), `module_tables_missing` (в копии
  есть строки таблицы, которой у модуля на цели нет — модуль старее копии) и
  `module_restore_conflict` (уникальное значение занято другой записью). План показывает
  причину, ответ применения несёт `module_id` и `field_path` (имя таблицы/колонки, без значений).
- **Выход из блокировки**: план несёт `module_data.blocked_modules` (модули, из-за которых
  restore заблокирован) и `module_data.excluded` (исключённые запросом `exclude_modules`). Окно
  копии даёт «Восстановить без модуля …»: план строится заново с `exclude_modules=[id]`, и
  применение идёт с тем же списком — данные исключённого модуля на цели не меняются.
- **Откат по журналу прежней сборки**: `SqliteModuleStore.restore_full` не трогает таблицы (и
  настройки), которых нет в pre-image. Журнал, оставшийся от сборки с другим составом таблиц, не
  стирает таблицы, появившиеся в новой спецификации (заказы, коды QR/NFC).
- **Pre-image — все столбцы** (16.10.2026, R-151): `SqliteModuleStore.full_snapshot` читает строки
  спек-таблиц `SELECT *` (байты — `{"$b64": …}`), `restore_full` вставляет пересечение столбцов
  строки с `PRAGMA table_info`. Откат неудачного восстановления больше не сбрасывает столбцы,
  которые добавила более новая версия модуля, а провайдер ядра ещё не знает. Экспорт по-прежнему
  читает только столбцы спецификации; журнал прежнего формата восстанавливается как раньше.
- **Схема модуля новее ридера** → безопасный отказ секции/atomic-набора, без догадок.

## Защита входом при восстановлении (R-128, arch-auth-07)

Пользователи в копию не входят. Поэтому копия с включённой защитой входом, восстановленная на
компьютер без активного администратора, НЕ включает защиту: план помечает ключ
`security_enabled` как `held` и пишет «В копии включена защита входом, но на этом компьютере нет
администратора. Защита останется выключенной…» (`security_held_no_admin`), применение этот ключ
не пишет. Сбой проверки администратора считается «нет». Правило одно для плана и применения
(`restore_plan.security_hold_keys`); хранилище без `enabled_admin_state` (тестовое) ведёт себя как
раньше. Если флаг защиты восстановлением действительно меняется (в любую сторону), и план, и
результат применения требуют перезапуска — процесс читает флаг только при запуске, и без
перезапуска смена сработала бы молча потом.

## Multi-store атомарность

Core и модули — разные файлы; одна SQLite-транзакция их не покрывает. Журнал восстановления
хранит **pre-image каждого хранилища + SHA-256** до применения. Порядок применения документирован:
`core → модули (по module_id)`; откат — строго **обратный**, откатываются **все** выбранные
хранилища (включая упавшее посреди apply); каждый откат проверяется по SHA pre-image. Состояния:
`prepared → staging_modules → applying_core → applying_module:<id> → committed_pending_verify →
verifying_core → verifying_module:<id> → complete` (сбой → `rolling_back_module:<id> →
rolling_back_core → complete|rollback_required`). Нельзя получить «core восстановлен + Inventory
старый» и наоборот. Pre-images затираются только после общей verification. Физический снапшот
БД разрешён ТОЛЬКО как внутренний rollback-механизм; канонический пользовательский backup —
логический. Архив всей DATA_DIR **не является** пользовательской резервной копией.

## Frozen-фикстуры

`tools/fixtures/config_backup/module_data/` — замороженная фикстура payload v2 с module_data
(синтетика, SHA-256). После выпуска неизменяема; авто-перечисляется
`test_config_backup_compatibility_forever.py` вместе с v1/v2.
