# Подключение UI-проверки к исполнителю

UI-шаг закрывается только тогда, когда доказано **всё сразу**: оснастка квалифицирована,
квалификация относится к текущему окружению, и каждый изменённый участок интерфейса покрыт
зарегистрированным сценарием. Один сценарий настроек не превращается в доказательство
всего интерфейса.

```bash
python tools/validation/run_profile.py --working-tree --execute --with-ui
```

---

## 1. Два разных доказательства

| | Квалификация ИНСТРУМЕНТА | Доказательство ЗАДАЧИ |
|---|---|---|
| Что подтверждает | верификатор, драйвер, сторож сети и сценарии ведут себя предсказуемо | работает именно изменённый кандидат |
| Откуда берётся | серия этапа 3C, десять циклов | новые UI-прогоны после каждой правки |
| Наследуется | да, пока оснастка и окружение не менялись | **никогда** |
| Живёт в | [qualification.json](../../tools/validation/ui/qualification.json) | `logs/ui_runs/<run-id>/` конкретной задачи |

Повторять десять циклов после каждой правки продукта не нужно. Но и объявлять задачу
проверенной по старой серии нельзя: изменение `web/*` требует новых прогонов.

## 2. Сертификат и что его убивает

`qualification.json` выписывается **только** из фактически проверенных артефактов серии:
статус `QUALIFIED`, десять циклов, двадцать прогонов, ноль индивидуальных повторов, пустой
список невыполненных критериев. Он привязан к отпечатку исходных артефактов
(`source_artifact_digest`) и к отпечаткам самой оснастки.

Квалификацию **аннулирует** изменение: `run_ui_verification.py`, `_ui_driver.mjs`,
`_stage_server.py`, `network_guard/sitecustomize.py`, `scenarios.json`,
`select_ui_coverage.py`, `ui_coverage_map.json`, а также формата обязательных проверок,
порядка уборки процессов и сетевой политики.

Квалификацию **не аннулирует** изменение `server.py`, `app/`, `web/`, `modules/` — но такое
изменение требует нового прогона по задаче.

### Политика окружения

| Что | Правило | Почему |
|---|---|---|
| сборка Windows | должна совпадать | другая сборка — другое поведение процессов и портов |
| Python | `major.minor` должны совпадать | смена минорной версии меняет поведение стандартной библиотеки |
| Node | мажорная версия должна совпадать | мост CDP живёт на его `fetch` и `WebSocket` |
| движок браузера, мажорная | должна совпадать → иначе `STALE_ENVIRONMENT` | обновление Edge уже ломало автоматизацию: `--dump-dom` начал печатать пустоту |
| движок браузера, патч | квалификацию **не** убивает, но выдаёт предупреждение | патч обычно безобиден, но молчать о нём после того случая нельзя |

Проверка: `python tools/validation/ui/verify_qualification.py`. Статусы: `VALID`,
`STALE_TOOLING`, `STALE_SCENARIOS`, `STALE_ENVIRONMENT`, `MISSING`, `INVALID`.

## 3. Карта покрытия

[ui_coverage_map.json](../../tools/validation/ui/ui_coverage_map.json) — **отдельный**
источник правды, не смешанный с картой риска. Карта риска решает, какой профиль нужен;
карта покрытия — какой кусок интерфейса реально проверен.

Зарегистрирована одна единица: **`settings_panel_shell`** — оболочка экрана настроек. Она
требует **оба** сценария: `settings_panel_open_close` и `settings_panel_open_close_isolated`.

Разрешённые маркеры взяты из настоящего кода: `openSettings`, `closeSettings`,
`showSettings`, `fm-settings-workspace`, `fm-set-title`, `fm-set-x`, `data-tour="settings"`,
`fm-boot-fallback`. Широких слов вроде `settings`, `button` или `app` среди них нет.

Явно **не покрыто**: содержимое панели (`fm-set-nav`, вкладки, группы, элементы управления,
установка модулей), закрытие кликом по затемнению, геометрия окна и липкая навигация, общий
менеджер оверлеев, верхняя панель, навигация между экранами, глобальные CSS-токены, любые
изменения backend.

## 4. Покрытие считается по diff, а не по пути

[select_ui_coverage.py](../../tools/validation/ui/select_ui_coverage.py) разбирает настоящий
unified diff и решает по каждому изменённому участку отдельно. Участок покрыт, если:

1. файл входит в пути единицы покрытия, **и**
2. в участке нет ни одного запретного маркера (ни в изменённых строках, ни в контексте), **и**
3. **каждая** изменённая строка содержит разрешённый маркер — **либо** участок стоит внутри
   оболочки настроек (якорь в контексте) и не добавляет нового интерактивного элемента.

Третье правило и есть причина, по которой правка CSS внутри `.fm-settings-workspace`
покрыта, а добавление новой кнопки с `@click` внутри той же секции — нет: сценарий её
не нажимает.

Правила: каждый участок обязан быть покрыт; один покрытый не прячет соседний непокрытый;
переименование анализируется по обоим путям; удаление UI-кода тоже требует покрытия;
неизвестное всегда остаётся непокрытым.

Статусы: `COVERED`, `PARTIALLY_COVERED`, `UNCOVERED`, `NO_UI_CHANGES`, `UNKNOWN`,
`INVALID_DIFF`.

## 5. Почему пути недостаточно

`--files web/app.css` не говорит, **что** в файле изменилось. В одном `web/app.js` живут
и настройки, и очередь печати, и менеджер оверлеев. Поэтому режим без diff даёт
`ui_coverage_status = UNKNOWN`, сценарии не выдаются, UI не запускается, а требование
остаётся открытым — итог не выше `PARTIAL`.

## 6. Поведение `--with-ui`

| Условие | Что происходит | Статус UI |
|---|---|---|
| изменение без UI | ничего | `UI_NOT_REQUIRED` |
| без `--with-ui` | UI не запускается, требование остаётся | `UI_NOT_REQUESTED` |
| квалификация не `VALID` | UI не запускается, общий `BLOCKED` | `UI_QUALIFICATION_STALE` |
| покрытие `UNKNOWN` | UI не запускается | `UI_COVERAGE_UNKNOWN` |
| покрытие `UNCOVERED` | UI не запускается, перечислены участки | `UI_UNCOVERED` |
| покрытие частичное | UI не запускается | `UI_PARTIALLY_COVERED` |
| всё доказано | оба сценария последовательно, static → isolated | `UI_PASS` / `UI_FAIL` |

**Сценарии выбирает карта покрытия, а не пользователь и не агент.** У исполнителя нет
аргумента `--ui-scenario` и нет способа передать URL. Повторов нет: первый красный сценарий
останавливает второй.

`UI_PASS` закрывает **только** признак `ui_required`. Он не заменяет SUBSYSTEM, RELEASE,
HARDWARE, сборку, mutation proof и проверку на железе. При профиле RELEASE или HARDWARE
исполнитель по-прежнему возвращает `BLOCKED`, и `--with-ui` обходом не служит.

## 7. Артефакты

В `logs/validation_runs/<run-id>/` добавляются `ui_qualification.json`, `ui_coverage.json`,
`ui_execution_plan.json`, `ui_results.json` и относительные ссылки на
`logs/ui_runs/<ui-run-id>/`. Снимки **не копируются**. Абсолютный путь рабочей папки
владельца не сохраняется.

`summary.json` расширен полями `ui_requested`, `ui_qualification_status`,
`ui_coverage_status`, `ui_coverage_units`, `ui_required_scenarios`, `ui_executed_scenarios`,
`ui_passed_scenarios`, `ui_failed_scenarios`, `ui_uncovered_hunks`, `ui_status`,
`ui_artifact_paths`.

## 8. Служебный дымовой прогон

`--ui-maintenance-smoke --execute` доказывает только проводку «исполнитель → верификатор».
Он не принимает путей, сценариев и URL, требует `VALID` квалификацию, запускает
квалифицированную пару и возвращает `UI_INTEGRATION_SMOKE_PASS` либо
`UI_INTEGRATION_SMOKE_FAIL`. **Общим `PASS` задачи он не становится никогда** — итог
остаётся `PARTIAL`.

## 9. Границы

Покрыта **оболочка одного экрана**. Не покрыты: содержимое настроек, остальные экраны,
печать, очередь, принтеры, файлы, склад, модули, адаптивность, зум и языковая матрица.
Статический сценарий ничего не доказывает про backend — это делает изолированный.
Изолированный экземпляр всегда свежий, поэтому поведение на данных владельца не проверяется.

Квалификация привязана к машине и окружению: другой ПК или мажорное обновление Edge требуют
новой серии ([ui-stability.md](ui-stability.md)).
