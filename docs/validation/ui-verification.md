# Проверка интерфейса в изолированном окружении

Верификатор открывает настоящий интерфейс в headless-браузере, выполняет один декларативный
сценарий и отвечает на вопрос, который не может закрыть чтение исходника: **отрисовалось ли
это на самом деле и меняется ли состояние от действий пользователя.**

```bash
python tools/validation/ui/run_ui_verification.py --scenario settings_panel_open_close
```

```bash
python tools/validation/ui/run_ui_verification.py --scenario settings_panel_open_close --execute
```

---

## 1. Два режима приложения

| Режим | Что запускается | Что этим доказано |
|---|---|---|
| **static_harness** | локальный статический сервер отдаёт **реальные** `web/index.html`, `app.js`, `app.css` и вендорный Vue; ответы `/api` синтетические | фронтенд действительно монтируется и реагирует; серверная логика **не** проверена |
| **isolated_farm_manager** | настоящий `server.py` в отдельной папке данных через штатный флаг `--fm-packaged-e2e` | приложение целиком |

Режим пишется в `summary.json` дословно и **не приукрашивается**. `coverage_scope` у двух
режимов разный, и статический прогон никогда не выдаётся за проверку backend.

### Официальный контракт изоляции

`isolated_farm_manager` запускает настоящий `server.py` **только** через штатный механизм
продукта — `app/e2e_isolation.py`. Ни одного нового флага и ни одной новой переменной
верификатор не изобретает.

| Параметр | Значение для верификатора | Что отключает |
|---|---|---|
| `--fm-packaged-e2e` | обязательный аргумент | без него `FM_E2E_*` игнорируются целиком |
| `FM_E2E_SENTINEL` | одноразовый токен, он же в `.fm-e2e-marker` | доказывает, что папку готовил именно этот запуск |
| `FM_E2E_DATA_DIR` | `logs/ui_runs/<run-id>/test_data` | рабочая папка владельца не используется |
| `FM_E2E_CONFIG_PATH` | `<data_dir>/config.json` | настройки владельца не читаются и не пишутся |
| `FM_E2E_MUTEX_NAME` | `Local\3DIWELL_FM_UI_<run-id>` | тест не конкурирует с работающей программой |
| `FM_E2E_PORT` | случайный свободный порт петли | обычный порт владельца не занимается |
| `FM_E2E_DISABLE_TRAY` | `1` | системный трей |
| `FM_E2E_DISABLE_BROWSER` | `1` | автооткрытие браузера владельца |
| `FM_E2E_DISABLE_DISCOVERY` | `1` | обнаружение принтеров в сети |
| `FM_E2E_DISABLE_PRINTERS` | `1` | опрос принтеров |
| `FM_E2E_DISABLE_MODULES` | `1` | загрузка модулей |

Контракт **fail-closed**: продукт отказывается стартовать (`E2E isolation rejected: <код>`,
выход 3), если токен короче 16 символов, папка не существует, содержит ссылку/стык, совпадает
с рабочей или лежит внутри неё, маркер не совпал, mutex рабочий или config вне папки.
Отдельно есть `tools/test_packaged_restart_end_to_end.py`, который этот же контракт проверяет.

Dispatch и transport официальными переменными не управляются: они доказываются исходными
значениями `False` и тем, что тестовый config не содержит `project_print_enabled`.
Read-only эндпоинта состояния предохранителей в продукте нет — способ доказательства указан
в `backend_assertions.json` дословно.

**Проверка обновлений.** Принятый контракт изоляции сам по себе запрещает внешние обращения:
`Isolation.disable_update_check` — свойство принятой изоляции, а не переменная окружения,
поэтому включить его иначе, чем пройдя весь официальный контракт, невозможно. Обработчик
`/api/update-check` спрашивает решение у объекта контракта и возвращает ответ той же формы,
что и при недоступном сайте. **Обычный запуск не меняется вовсе**: адрес манифеста, тайм-аут,
кэш, разбор ответа и баннер в интерфейсе те же, а отдельного выключателя обновлений у
пользователя не появилось. Сторож сети остаётся независимым доказательством: исключения для
домена обновлений в нём нет и быть не должно.

## 2. Изоляция

Каждый запуск получает собственный каталог `logs/ui_runs/<run-id>/` (каталог `logs/` игнорируется
Git) со структурой `test_data/`, `browser_profile/`, `artifacts/`, `process_logs/`.

До запуска браузера и сервера доказывается всё перечисленное; **любое непройденное условие
блокирует запуск**, а не понижает требования:

- тестовая папка данных и профиль браузера лежат **внутри** каталога запуска;
- каталог запуска лежит внутри игнорируемого `logs/`;
- тестовая папка данных создана пустой — она **не копируется** из рабочей;
- рабочая папка владельца не является ни родителем, ни потомком тестовой
  (её путь в артефакты не попадает — сохраняется только отпечаток SHA-256);
- порт выбран на `127.0.0.1` и свободен;
- `DISPATCH_ENABLED` и `TRANSPORT_ENABLED` подтверждены как `False`;
- в сценарии нет адресов реальных устройств и учётных данных;
- движок браузера найден в **контролируемом списке** установленных путей.

Рабочая папка владельца читается только ради сравнения путей; её содержимое и БД не
открываются никогда.

## 3. Сетевая политика

Разрешены только `127.0.0.1`, `localhost`, собственный случайный порт запуска, а также
`data:`, `about:` и `blob:`. Всё остальное — **FAIL**, а не строчка в журнале.

**Браузер.** Запускается с `--host-resolver-rules=MAP * ~NOTFOUND , EXCLUDE 127.0.0.1`,
поэтому чужое имя физически не разрешается. Параллельно ведётся журнал: Resource Timing
покрывает всё, что страница загрузила с самого начала, а обёртки `fetch`, `XMLHttpRequest`,
`WebSocket` и `EventSource` — фазу действий. Итог целиком лежит в `network_attempts.json`.

**Backend.** Журнал браузера ничего не говорит про сам Python-процесс. Поэтому в изолированном
режиме подключается сторож `tools/validation/ui/network_guard/sitecustomize.py`: Python сам
импортирует его при старте, каталог подкладывается **только** этому подпроцессу через
`PYTHONPATH`. Сторож подменяет `connect`, `connect_ex` и `sendto` и пропускает исключительно
петлю; всё остальное блокируется **до** выполнения. Разрешение имени не блокируется, но
записывается — соединение всё равно не состоится.

Предохранитель сторожа: без переменных `FM_UI_GUARD_LOG` и `FM_UI_GUARD_SENTINEL` он не делает
ничего, поэтому подложить его рабочей программе и подменить ей сеть нельзя. Глобальный Python
не изменяется. В журнал попадают только время, PID, хост, порт, решение и причина —
ни байта передаваемых данных.

**Отсутствие удостоверения сторожа блокирует запуск**: без доказательства, что он загрузился,
изоляция backend недоказуема.

## 4. Процессы и уборка

Все процессы запускаются без видимого окна, `stdout`/`stderr` — в отдельные файлы,
последовательно, с жёстким таймаутом, PID записывается в `process_manifest.json`.

Порядок уборки: сессия браузера → собственный браузер → собственный локальный сервер →
проверка освобождения порта → проверка отсутствия своих процессов.

**Процессы не ищутся по имени.** `taskkill` вызывается только как `/PID <pid> /T /F`;
`/IM` не используется нигде. Браузер и python владельца задеть невозможно: гасятся только
PID, записанные этим запуском. Профиль браузера владельца не используется — профиль всегда
создаётся внутри каталога запуска.

Если сервер завершился раньше готовности, это **FAIL**, и код возврата `0` успехом не
считается: именно так выглядит программа, которая упала на именованном мьютексе, не выполнив
ни одной проверки.

## 5. Статусы и коды возврата

| Статус | Значение | Код |
|---|---|---|
| **PASS** | все обязательные проверки DOM пройдены, консоль чиста, наружу обращений нет | 0 |
| **DRY_RUN** | показан план, **не запущено ничего** | 0 |
| **FAIL** | красная проверка, ошибка консоли, внешнее обращение или аварийный выход | 2 |
| **BLOCKED** | изоляция не доказана либо режим на этом этапе не выполняется | 3 |
| **TIMEOUT** | сценарий не уложился в бюджет | 4 |
| **CONFIG_ERROR** | сценарий не найден, реестр повреждён или запрещён по содержимому | 5 |

## 6. Формат сценария

Сценарий — это **данные**, а не программа. В
[scenarios.json](../../tools/validation/ui/scenarios.json) запрещены произвольный Python,
произвольный JavaScript, shell-команды, внешние URL и адреса принтеров; загрузчик отклоняет
такой сценарий. Пользователь выбирает сценарий **только по `id`** — передать свой URL, свою
команду или свой путь к браузеру нельзя.

Допустимые действия: `wait_for_selector`, `click`, `fill`, `press`, `set_viewport`,
`screenshot`, `read_text`, `assert_visible`, `assert_hidden`, `assert_text`,
`assert_attribute`. Селектор уходит в страницу только через `JSON.stringify`.

Помимо списка действий сценарий объявляет `assertions` — обязательные проверки с
идентификаторами. Верификатор сверяет, что **каждая** из них действительно выполнена и
зелёная. Это двойная запись: молча пропущенная проверка не превратится в зелёный итог.

## 7. Почему скриншот ничего не доказывает

Страница может отрисовать заглушку загрузки, показать пустой контейнер или застыть на
прошлом кадре — на снимке это выглядит правдоподобно. Поэтому снимки **не влияют на вердикт**:
без пройденных обязательных проверок DOM результат не может быть `PASS`, и отдельной проверкой
закреплено, что одни только скриншоты дают `FAIL`.

Снимки — доказательство для человека, а не аргумент для автоматики. В пилоте их три:
до действия, после открытия панели и после её закрытия; первый и третий побайтово совпадают —
именно так выглядит восстановленное состояние.

## 8. Артефакты

`logs/ui_runs/<run-id>/`: `summary.json`, `summary.txt`, `scenario.json`, `console.json`,
`network_attempts.json`, `dom_assertions.json`, `environment.json`, `process_manifest.json`,
`artifacts/*.png`, `process_logs/*.stdout.txt` и `*.stderr.txt`.

Артефакты создаются **только** при `--execute`. Секреты в них попасть не могут: дочерние
процессы получают лишь список разрешённых переменных окружения, а рабочий путь данных
сохраняется отпечатком, а не текстом.

## 8a. Готовность, backend и файловая система (изолированный режим)

**Готовность.** Открытый порт готовностью не считается. Подтверждаются десять условий:
процесс жив; получен официальный ответ `/version`; ответ пришёл с порта этого запуска;
контракт изоляции принят продуктом; удостоверение сторожа сети есть; тестовая папка данных
действительно использована; рабочая папка не использована; dispatch и transport эффективно
выключены; в выводе нет `E2E isolation rejected` и трассировок; всё это уложилось в срок.
Доказательство — `readiness.json`. **Ранний выход сервера с любым кодом, включая 0, — FAIL**,
и браузер после этого не запускается.

**Backend-проверки.** Выполняются **до** запуска браузера и только по существующим read-only
эндпоинтам: `/version` (ответ и версия), `/api/printers` (пусто), `/api/send-jobs` (нет
очереди и резервов), `/api/modules` (ответ с локального порта). Ничего не создаётся, не
удаляется и не изменяется. Там, где read-only эндпоинта не существует (режим изоляции,
состояние предохранителей), способ доказательства назван прямо: созданные в тестовой папке
файлы и отсутствие `project_print_enabled` в тестовом config.

**Файловая система.** После сценария проверяется: тестовая папка создана; путь config внутри
каталога запуска; все найденные БД лежат внутри тестовой папки и по размеру соответствуют
свежей установке, а не копии рабочей; все файлы рантайма внутри каталога запуска; отпечаток
рабочей папки владельца **до и после совпал**; продуктовые файлы репозитория не изменились.
Отпечаток снимается по именам, размерам и времени — содержимое не читается, абсолютный путь
в артефакты не попадает.

## 9. Границы пилота и что нужно этапу 3B

Пилот `settings_panel_open_close` проверяет отрисовку корневого экрана, доступность реального
интерактивного элемента, открытие панели настроек, её содержимое и восстановление исходного
состояния. Это **один экран**, а не интерфейс целиком.

Этап 3B добавил второй сценарий — `settings_panel_open_close_isolated`, тот же по смыслу, но
на настоящем `server.py`. Сравнение двух прогонов и есть смысл пары: расхождение показывает,
где статический стенд врёт.

Известные ограничения:

- **проверен один экран** — это не проверка продукта, печати или оборудования;
- в `static_harness` ответы `/api` синтетические, поэтому статический прогон **не является**
  доказательством работы backend; каталог `test_data/` там создаётся, но остаётся пустым;
- изолированный экземпляр — свежая установка: пустая БД, нет принтеров, нет проектов.
  Поведение на данных владельца не проверяется и проверяться не будет;
- проверок раскладки, зума и адаптивности нет;
- верификатор **не подключён** к [run_profile.py](profile-execution.md): признак `ui_required`
  по-прежнему даёт `PARTIAL`. Делать UI-проверку обязательным шагом можно только после того,
  как она наберёт статистику стабильности — иначе хрупкий браузерный шаг начнёт красить
  безобидные правки.

**Что нашёл первый настоящий прогон и чем закончилось.** Изолированный экземпляр с
выключенными трееем, браузером, обнаружением, принтерами и модулями всё равно попытался
открыть исходящее HTTPS-соединение к сайту за манифестом обновлений; сторож заблокировал,
запуск честно получил `FAIL`. Дефект закрыт отдельной задачей: принятая изоляция теперь сама
запрещает проверку обновлений. Подтверждающий прогон — `PASS`: заблокированных попыток 0,
исходящих соединений backend только петля, имя сайта даже не резолвилось.

Подавление подтверждается **двумя независимыми способами**, а не только тем, что сторож
никого не пустил: ответ `/api/update-check` (`ok=false`, без новых попыток соединения) и
строка `E2E isolation: update check disabled` в выводе принятого контракта.

Этапу 3C понадобится: критерий стабильности перед подключением UI-шага к исполнителю
и несколько сценариев вместо одного.

Стабильность этих сценариев измеряется отдельно — [ui-stability.md](ui-stability.md):
десять последовательных циклов без единого повтора. `QUALIFIED` относится к серии,
`PASS` — к одному прогону. Как эти сценарии подключаются к исполнителю и почему
путь файла покрытием не считается — [ui-executor-integration.md](ui-executor-integration.md).
