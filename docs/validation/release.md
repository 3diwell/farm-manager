# Релиз: полный gate, версия, сборка

Читать **только когда задача действительно требует релиза** — то есть когда результат
передаётся владельцу для установки либо затронута критическая область
([critical-runtime.md](critical-runtime.md)).

Рутинная правка релиза **не требует**. Когда что запускать — CLAUDE.md §3.

## 1. Полный release gate

**Запускается по слову владельца** (его решение от 04.09.2026). Перед сборкой, которую он
поставит себе или отдаст бета-тестеру, я предлагаю прогон и жду ответа — там цена ошибки его.

```bash
python tools/release_gate.py          # весь набор; --list печатает манифест, ничего не запуская
```

Раннер **не изменяется и не ослабляется**. Он сам:

- строит манифест без исключений (все `tools/test_*.py` и `tools/test_*.mjs`);
- сохраняет отдельные `stdout` и `stderr` на каждый файл, `manifest.json`, `results.json`
  (пишется после каждого файла), `summary.json`, `runner.log` в
  `C:\3DIWELL_Builds\logs\release_gate_2.841\<run-id>\` — **вне репозитория**;
- считает результат строго: машиночитаемая строка → сводка мутаций → точная сводная форма →
  построчный протокол. **Нераспознанный формат = `unknown` = красный**, нулём не становится;
- выдаёт наборам временную папку **на диске репозитория** (`gate_tmp_dir`), когда системный
  `TEMP` лежит на другом диске. Иначе часть наборов падает в `os.path.relpath`
  («path is on mount 'C:', start on mount 'D:'») ещё до своих проверок: они не выполняются
  вовсе, а гейт показывает их красными — настоящая поломка внутри осталась бы незамеченной.
  Каталог создаётся рядом с папкой проекта (`_3diwell_gate_tmp`), и его имя НЕ начинается
  с пути репозитория: наборы-песочницы проверяют себя условиями «REPO not in ROOT» и
  «not ROOT.startswith(REPO)», поэтому имя вида `<репозиторий>.gate_tmp` роняет семь ранее
  зелёных наборов. Внутрь репозитория временные файлы класть нельзя тем более — их поймает
  проверка гигиены. Системный `TEMP` уже на нужном диске — подмены не происходит.
  Правило закреплено набором `tools/test_release_gate_tmp_isolation.py`.

`rc = 0` допускается только при нулевых: red, unknown, error, timeout, excluded, fail_checks,
skip_checks, unknown_skip_files, internal_mutation_failures, mutation_not_applied,
unexpected_green, restore_failures, cleanup_failures.

Ориентир: **304 файла, около 1 ч 25 мин** (13.10.2026); бОльшую часть времени занимают mutation proof.

**Mutation proof портят файлы репозитория.** Общий замок `tools/_mutation_lock.py` сериализует
прогоны; параллельный запуск уже приводил к тому, что откат одного затирал откат другого.
Во время прогона `git status` показывает чужие мутации — не верить ему и ничего не править.

## 2. Версия

`APP_VERSION` в `server.py` — **единый источник**, формат `"Alpha <старшая>.<младшая>"` или
`"Beta <старшая>.<младшая>"` (с 12.09.2026 — `"Alpha 3.0"`, с 25.10.2026 — `"Beta 3.71"`;
разборщики читают номер парой чисел и принимают оба префикса). Номер всегда читать
из файла, не из памяти.

**Когда поднимать — по CLAUDE.md §8** (при каждом изменении кода;
там же — про заморозку номера файлом `.ai/VERSION_FREEZE`).
Здесь описано только ЧТО обновлять синхронно:

- `3diwell-setup.iss` и `3diwell-client-setup.iss` — `#define AppVersion`
- `desktop_shell_version_local.txt` и `desktop_shell_version_client.txt` — `filevers`,
  `prodvers`, `FileVersion`, `ProductVersion`

Итого пять мест. Отдельного файла `CHANGELOG.md` в репозитории нет; журнал «Что нового»
живёт константой `CHANGELOG` внутри `server.py` (новые записи сверху).

## 3. Сборка

**Выпуск целиком — одной командой (с 3.0):**

```bash
python tools/build_release.py
```

Она делает по порядку: три EXE (сервер — системным Python по `3diwell.spec`, оболочки —
интерпретатором `buildenv` по `desktop_shell.spec`), удостоверение `e2e-supported.txt`,
packaged proof (§4), сверку текстов лицензий (ниже), стенд «папка без права записи» (§4), оба
установщика Inno Setup с вложенными компонентами Windows, пересборку ZIP всех модулей и папку
выпуска `C:\3DIWELL_Builds\Release_<версия>\` с установщиком, модулями, `ПРОЧТИ МЕНЯ.txt`,
`BUILD_ENVIRONMENT.txt` (чем собрано, без путей компьютера) и `SHA256SUMS.txt`. Красный шаг
останавливает всё. Ключи: `--skip-exe` (EXE уже в staging), `--no-stand` (без стенда — сборка
не считается проверенной). Полный прогон (§1) она не запускает. Пути можно переопределить
переменными `FM_BUILD_ROOT`, `FM_VENDOR_DIR`, `FM_SHELL_PYTHON` (docs/dev/building.md).

**Тексты лицензий сторонних пакетов (R-130, 29.09.2026).** Установщик ставит всё `*.txt` из
`packaging/installer/licenses` в папку `licenses` рядом с программой, в том числе
`THIRD_PARTY_LICENSES.txt` — тексты лицензий всех пакетов Python внутри трёх EXE. Файл
отслеживается в git; сборка его НЕ пишет, а сверяет: `tools/collect_third_party_licenses.py`
читает состав каждого EXE (сервер — системным Python, оболочки — `buildenv`) и сравнивает с
файлом. Не совпало (обновили пакет) — выпуск останавливается и печатает команду обновления;
обновить, зафиксировать и повторить `python tools/build_release.py --skip-exe`.

**Компоненты Windows для установщика** лежат вне репозитория в `C:\3DIWELL_Builds\vendor`:
`MicrosoftEdgeWebView2RuntimeInstallerX64.exe` (~210 МБ) и `ndp48-x86-x64-allos-enu.exe`
(~120 МБ). Где взять и как проверить подпись Microsoft — в шапке
`tools/installer/prereqs.iss`. Без них сборка выпуска останавливается (`/DReleaseBuild`);
обычная компиляция `.iss` без них не ломается — просто без шага компонентов.

**`build.bat` из агента не запускать** — он содержит `pause` и удаляет рабочий `dist\`.
Собирать вручную, если нужно по шагам, staging уходит наружу:

```bash
python -m PyInstaller --noconfirm --clean \
  --distpath "C:/3DIWELL_Builds/Beta_<версия>/dist" \
  --workpath "C:/3DIWELL_Builds/work/<версия>/server" 3diwell.spec

"C:/3DIWELL_Builds/buildenv/Scripts/python.exe" -m PyInstaller --noconfirm --clean \
  --distpath "C:/3DIWELL_Builds/Beta_<версия>/dist" \
  --workpath "C:/3DIWELL_Builds/work/<версия>/shell" desktop_shell.spec

ISCC.exe /DDistDir="C:\3DIWELL_Builds\Beta_<версия>\dist" /DReleaseBuild /O"куда" 3diwell-setup.iss
```

Сервер собирается **системным Python**, оболочки — интерпретатором `buildenv`.
**Рабочие `dist\*.exe` не перезаписывать** — их заменяет владелец вручную.

`buildenv` не переносится между компьютерами: после переноса по USB в `pyvenv.cfg` остаются
чужие пути, их чинят вручную.

## 4. Packaged proof

После сборки — доказать, что новый код **внутри** EXE: распаковать архив, достать объекты кода
и проверить имена функций и константы. Проверка по внешнему TOC ложна в обе стороны: `fastapi`,
`uvicorn` и модули `app/*` живут в PYZ.

**server-EXE не запускать С АРГУМЕНТАМИ** — флага версии у него нет, любой нераспознанный
аргумент запустит всю программу.

### Запуск из папки без права записи — ОБЯЗАТЕЛЬНО

Одного доказательства «код внутри EXE» НЕ ХВАТАЕТ. 02.09.2026 сборка 2.939 прошла packaged
proof на 25 из 25 и была отдана владельцу — и не запустилась у него вовсе: сервер падал на
`server.py:769` с `PermissionError [WinError 5]`, пытаясь создать `thumb_cache` внутри
`C:\Program Files\3DIWELL Farm Manager`. На машине разработки сборка лежит в обычной папке,
поэтому ни один статический разбор этого не видел.

Условие воспроизводится так (стенд, ничего в системе не меняет):

1. временная папка, в ней `icacls <папка> /deny "%USERNAME%":(WD,AD)` — право создавать файлы
   и подпапки снято; убедиться, что `os.makedirs` внутрь неё действительно падает;
2. положить туда собранный `3DIWELL Farm Manager.exe` и запустить **без аргументов**, задав
   свои `LOCALAPPDATA` и `APPDATA` на временную папку — настоящие базы владельца не участвуют;
3. через 20 секунд остановить процесс по его PID и снять запрет.

Зелёным считается только это: процесс дожил до конца отсчёта, в журнале есть строка
`lifespan: YIELD`, `PermissionError` в выводе нет. Хорошая привычка — прогнать тем же стендом
ПРЕДЫДУЩУЮ сборку: она обязана вести себя так же, иначе стенд ничего не доказывает.

Статический сторож на ту же тему — `tools/test_program_folder_not_written.py` (в полном
прогоне). Он ловит правку кода, стенд ловит правку окружения; нужны оба.

Отдельно снять SHA-256 трёх EXE и подтвердить, что рабочие `dist\*.exe` не изменились.

## 5. Модули

Изменён `modules/<id>/*` → поднять `"version"` в `module.json`, пересобрать zip
(`tools/build_<id>_zip.py`) и сказать владельцу переустановить модуль.
Подробности — [modules.md](modules.md).

## 6. Что фиксируется по завершении

- Одна строка в `.ai/action_log.jsonl`.
- Один коммит на задачу; отдельный handoff-коммит — только если задача этого прямо требует.
- `.ai/CURRENT_STATE.md` обновляется, **только если изменилось описанное там состояние**.

Какой профиль нужен для конкретной правки — [profile-selection.md](profile-selection.md).
