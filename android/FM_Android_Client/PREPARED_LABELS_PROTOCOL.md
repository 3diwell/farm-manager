# Предварительные этикетки — protocol 3 и цены protocol 5

## Дополнение 0.8: цена партии до приёмки

Текущий пакет: `dist/inventory-1.7.29-desktop-prices-0.8.0.zip`.
Маршруты и права прежние, `backend.py` совпадает с пакетом NFC 0.7 побайтово.
GET `/api/mod/inventory/filament` добавляет в `mobile.features` признак
`prepared_label_prices_v5`, в `mobile.currency` — валюту настройки склада
(`inv_settings.currency`, прежнее значение по умолчанию ILS).
Поле `mobile.protocol` остаётся 1 для совместимости.

Только подготовка **с ценой** использует `mobile.protocol=5`,
`mobile.operation=prepare_labels` и прежний POST `/api/mod/inventory/spool`.
Остальные поля партии прежние. Новое поле тела:

```json
{"pricing":{"mode":"total","amount":"12000.00"}}
```

`mode=total` — сумма всей партии; `mode=unit` — цена целой катушки, не килограмма.
`amount` — неотрицательная десятичная строка, максимум два знака после точки/запятой.
Клиент отправляет канонический вид с точкой. Число вместо строки, лишние поля pricing,
экспонента, отрицательные/нечисловые значения и сумма свыше 1 000 000 000 отклоняются.
Все расчёты распределения выполняются целыми сотыми, без округления float.
Количество прежнее: 1–500. Ноль разрешён; отсутствие цены не равно явно указанному нулю.

Подготовка без цены и Android-подготовка остаются protocol 3 без поля `pricing`.
На новом сервере protocol 3 + pricing отклоняется с `pricing_requires_protocol_5`.
На прежнем сервере protocol 5 отклоняется целиком: цена не теряется молча.
ПК также проверяет feature перед отправкой. При неизвестном результате запроса сохраняется
точное тело с ценой и исходным request_id; повтор не создаёт новую партию.

### Миграция и распределение

Повторяемая добавочная миграция в savepoint под `lock_inv` расширяет только реестр этикеток:

- `inv_mobile_label_batches`: `price_mode`, `price_quantity`, `price_input_minor`,
  `price_total_minor`, `price_currency`.
- `inv_mobile_labels`: `price_minor` (цена целой катушки в сотых).

У старых партий и меток числовые поля NULL; исторические `inv_spools.price` не изменяются.
Для новой партии сохраняются исходные количество, режим, сумма и валюта.
Если сумма не делится на количество, последние по ordinal метки получают по одной
дополнительной сотой. 100/3 → 33.33, 33.33, 33.34. Это определяется при подготовке,
а не в момент сканирования. Отмена/частичная приёмка/перезапуск ничего не перераспределяют.

`claim_label` остаётся protocol 3, поэтому Android 0.10 не обновляется.
Сервер берёт цену только из метки и записывает её в штатное `inv_spools.price`;
поля цены, подставленные в запрос claim, не используются.
Переход статуса, цена, катушка, приход и результат идемпотентности фиксируются вместе.
Повтор по уже принятой метке — прежний no-op, индивидуально изменённая цена сохраняется.
При NULL используется прежний ноль поля катушки. `inv_filaments.price_per_kg` не меняется;
прежний приоритет каталожной цены в существующих расчётах также не меняется.

Цена хранится на сервере, не в QR; формат `fm1:spool:<server_id>:<reserved_id>` прежний.
Печатные объекты/шаблоны не содержат цены. На ПК цена видна только в форме и реестре меток.
Отображаемая сумма партии — первоначальная, а не стоимость оставшихся или уже принятых меток.
Валюта фиксируется для пояснения в партии; автоматической конвертации при смене общей
валюты FM нет, как и в прежнем складе. Не меняйте валюту между подготовкой и приёмкой.

Редактирование цены уже подготовленной партии и перенос цены в старые партии не добавлены.
Не откатывайте модуль на 0.7 при наличии ожидающих меток с ценой: старый обработчик claim
не использует новые поля и примет катушку без этой цены. Дополнительные столбцы сами по себе
не обеспечивают сохранение поведения старого обработчика.

Ниже сохранено описание исходного протокола 3 версии 0.4. В актуальном Android 0.8–0.10
партия определяется автоматически в общей приёмке. Печатные шаблоны с Desktop Labels 0.5.2
не показывают массу и диаметр; упоминания старого интерфейса ниже исторические.

## Исходный протокол 3, расширение 0.4

## Совместимость и область

Новые HTTP-маршруты не добавлены: используется защищённый штатный POST
`/api/mod/inventory/spool` и его право на создание катушек. Метаданные возвращаются
через существующий GET `/filament`. Код ядра, маршруты, policy_id, print hooks,
интерфейс модуля и legacy-обработчики без mobile не изменены.
Старые клиенты продолжают протоколы 1/2; новые действия разрешены по feature
`prepared_labels_v3`, а сервер строго проверяет protocol=3 и допустимую операцию.
Протокол 3 нельзя отправить через bind; протокол 1/2 нельзя использовать для новых операций.
Модуль 0.2 отклоняет новые запросы, а не выполняет обычную приёмку вместо них.

## Данные

Две добавочные таблицы в той же SQLite под штатным lock_inv:

- inv_mobile_label_batches: id, name, filament_id, caption (снимок), weight_total_g,
  общая label, created_at.
- inv_mobile_labels: заранее выделенный spool ID, batch_id, ordinal, status
  (prepared/received/cancelled), location_id при приёмке, received_at, cancelled_at.

init использует CREATE TABLE IF NOT EXISTS; повторный запуск не меняет server_id,
катушки или старые партии. Подготовленные метки НЕ находятся в inv_spools, не участвуют
в остатках/FIFO/списании/привязке. При подготовке нового материала создаётся только запись
каталога, а не складской приход. Весь журнал подготовленных партий живёт в FM, не телефоне.

GET mobile metadata сохраняет protocol=1 и codes; дополнительно возвращает prepared_batches
и prepared_labels. Возвращаются все партии и метки; серверная пагинация ещё не реализована.
С учётом прежнего лимита ответа клиента 16 MiB очень большие архивы потребуют пагинации.

## Операции

Общий mobile envelope: protocol=3, operation, server_id, request_id.

- prepare_labels: name, filament_id ИЛИ filament, weight_total_g, quantity 1..500, label.
  Полностью атомарно создаются партия/метки/при необходимости материал и запись inv_mobile_ops.
  Ответ operation=prepare_labels, batch_id, counts; id катушки в ответе отсутствует.
- claim_label: batch_id, location, mobile.code. QR строго `fm1:spool:<server_id>:<reserved_id>`.
  Клиент не передаёт фактическую массу/материал: они берутся из партии. Проверяются
  членство в партии, статус, полка, актуальность материала относительно напечатанной подписи.
  Для prepared атомарно создаются inv_spools с тем же ID, обычный in в inv_ledger,
  переход received, location/time и результат inv_mobile_ops. Для received — успешный no-op
  already_received, даже при удалённой/списанной катушке. Для cancelled — отказ.
- cancel_labels: batch_id, label_ids (явный список уникальных ID 1..500).
  Только prepared становятся cancelled; received не изменяются. Неизвестный ID отменяет
  всю транзакцию. Возвращаются cancelled_count и counts.

Идемпотентность всех действий: BEGIN IMMEDIATE + lock_inv, хеш тела/операции,
результат в inv_mobile_ops в той же транзакции. При одинаковом request_id возвращается
сохранённый результат, отличающееся тело отвергается. Новый request_id со старой принятой
меткой возвращает no-op по статусу метки. Два клиента и гонка cancel/claim сериализуются.

## Android

Запрос и контекст сохраняются ДО отправки прежним журналом pending. Создание/отмена/приёмка
подготовленных меток отделены от обычной приёмки: ответы без spool id не попадают в ReceiptBook.
После включения оператором режима для конкретной партии и полки скан сразу отправляет claim;
следующий скан разрешён после ответа FM. Камера не остаётся в непрерывном режиме.
Передача QR между телефонами не переносит сеансы/пароли. Метки используют прежний формат,
поэтому после claim подходят для прежней привязки. Обычная приёмка по произвольному fm1
по-прежнему запрещена; метка не является авторизацией и сама по себе не выполняет HTTP-вызов.

Повторный PDF использует те же ID, исключает отменённые метки. Печатная метка не содержит
статус «ожидает», чтобы не стать неверной после приёмки; статус показывается только в FM.
Масса подписи явно обозначена как масса при приёмке, не текущий остаток.
